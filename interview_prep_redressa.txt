REDRESSA - COMPLETE INTERVIEW / SHORTLISTING PREP NOTES

This file is written in simple English.
Read it to understand the project properly.
Do not memorize it word for word.

--------------------------------------------------
1. ONE-LINE SUMMARY
--------------------------------------------------

Redressa is a consumer redressal workflow platform.
It helps users turn messy complaints and evidence into structured, escalation-ready action.

Simple version:
"If customer support fails, Redressa helps the user understand the case, organize the evidence, and prepare the next escalation step."


--------------------------------------------------
2. WHAT PROBLEM ARE WE SOLVING?
--------------------------------------------------

Main problem:
Many users have valid complaints, but they do not know how to escalate them properly.

What usually happens:
- A person gets a refund issue, flight issue, damaged product issue, or service issue.
- They contact customer support.
- Customer support gives vague replies, delays, or rejects the request.
- The user gets confused and gives up.

Why this happens:
- They do not know what to say next.
- They do not know which evidence matters.
- They do not know where to escalate.
- Policies and rules are scattered across different documents and websites.

What makes this a real problem:
- A valid complaint is not enough.
- People need a structured way to move from complaint to action.

Strong line to say:
"The problem is not just complaint filing. The real problem is complaint escalation."


--------------------------------------------------
3. WHAT EXACTLY DOES REDRESSA DO?
--------------------------------------------------

Redressa takes:
- the complaint text
- merchant/company details
- amount/reference number
- uploaded evidence like screenshots, emails, receipts

Then it does a multi-step workflow:
1. Intake
2. OCR / parsing
3. Fact extraction
4. Timeline building
5. Policy and regulation retrieval
6. Evaluation
7. Route recommendation
8. Output generation
9. Communication workflow

Final result:
- structured case summary
- grievance email draft
- escalation note
- evidence checklist
- recommendation on next steps

Simple line:
"Redressa is not just giving advice. It is preparing the next action."


--------------------------------------------------
4. WHY THIS FITS TRACK 2
--------------------------------------------------

Track 2 is about agentic AI / AI workflows.

This project fits because:
- it is not one single LLM answer
- it has a multi-step pipeline
- each step does a specific job
- the output of one step becomes the input to the next
- the system performs a real-world task

Good answer:
"This is a workflow agent, not a chatbot wrapper. It takes evidence, reasons across multiple steps, and generates outputs a user can actually use."

12. HOW DOES THE PIPELINE WORK?
--------------------------------------------------

Simple explanation:

1. Intake
The user enters complaint details and uploads evidence.

2. Parsing
The system reads the complaint and files.

3. OCR
If the evidence is an image or screenshot, OCR extracts text.

4. Fact extraction
Important facts are pulled out:
- merchant
- amount
- dates
- references
- issue type

5. Timeline
The system organizes key events in order.

6. Retrieval
Relevant policy and regulation material is fetched.

7. Evaluation
The complaint is checked against that grounding.

8. Route recommendation
The system recommends likely next actions.

9. Output generation
It creates user-facing outputs such as email drafts and case summaries.

51. TECHNICAL QUESTION - OCR IS NOISY. HOW DID YOU HANDLE IT?
--------------------------------------------------

Best answer:

"Yes, OCR is noisy, especially with screenshots and PDFs. We did not treat OCR output as final truth. We treated it as an extraction layer. After OCR, we run structured fact extraction and only carry forward the facts that are useful for the workflow. We also kept the product narrow in scope so the evidence types are more manageable. In short, we reduced OCR risk by narrowing categories and by using later structured steps instead of trusting raw OCR blindly."

Shorter answer:

"OCR is imperfect, so we used it as an input layer, not as truth."


--------------------------------------------------
52. TECHNICAL QUESTION - LLMS HALLUCINATE. HOW DID YOU HANDLE THAT?
--------------------------------------------------

Best answer:

"That is exactly why we did not build this as a free-form chatbot. We grounded the workflow in complaint details, OCR output, and retrieved policy and regulatory context. So the model is not generating from nowhere. It is still not perfect, but we reduce hallucination risk by structuring the pipeline and by making retrieval part of the flow."

Shorter answer:

"We reduce hallucination risk by grounding and structuring the workflow instead of relying on one open-ended prompt."

Shorter answer:

55. TECHNICAL QUESTION - COMMUNICATION AUTOMATION OFTEN DOUBLE-SENDS OR DESYNCS. HOW DID YOU HANDLE IT?
--------------------------------------------------

Best answer:

"We actually faced that issue. The critical lesson was to separate true send success from non-critical logging failures. So if the email was actually sent, the API should return success instead of surfacing a false error because of a later non-critical update. We also tightened the UI state so demo sends do not visually revert or look unsent after success."

Shorter answer:

"We made the send path more idempotent and separated critical success from non-critical side effects."

--------------------------------------------------

Best answer:

"Breadth and data quality. The first weak points would likely be OCR inconsistency, merchant-policy coverage, and retrieval quality across more diverse complaint types. The core flow works, but scaling quality across many merchants is the harder production problem."

66. CAN THIS BE IMPLEMENTED FOR THE MERCHANT SIDE TOO?
--------------------------------------------------

Best answer:

"Yes, definitely. Right now we built it from the consumer side because that is where the complaint-friction problem is most obvious. But the same workflow logic can be adapted for merchants too. A merchant-side version could classify complaints, summarize evidence, retrieve internal policy, suggest response templates, and prioritize which cases need human review."

Stronger answer:

"The consumer version proves the workflow. The merchant version could become an internal complaint triage and response copilot."

If they ask whether both sides using AI is strange:

"Not really. It just means both sides become more structured and efficient. The consumer side gets better escalation. The merchant side gets better triage and response consistency."
